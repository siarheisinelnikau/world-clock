# Contributing

World Clock is a native Windows application written in Rust. Bug reports and focused pull requests are welcome.

For a bug report, include your Windows version, display scaling, taskbar configuration, steps to reproduce, and what you expected. Screenshots help with layout problems. Remove personal information from screenshots and diagnostic logs before sharing them.

## Development

Use 64-bit Windows, stable Rust with the `x86_64-pc-windows-msvc` toolchain, and Visual Studio C++ Build Tools with the Windows SDK.

```powershell
cargo run -- --settings
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
.\build.ps1
```

Check desktop click-through behavior, positioning, settings persistence, and taskbar placement manually when changing those features. Include the relevant checks in your pull request.

Quit a running copy from the tray before rebuilding into the same `dist/WorldClock-vVERSION.exe` path; Windows locks executables while they are running.

## Source map

| File | Responsibility |
| --- | --- |
| `src/app.rs` | Application windows, settings, tray, and event handling |
| `src/desktop.rs` | Keep desktop widgets visible when Explorer raises the desktop |
| `src/appearance.rs` | Card styles and the visual appearance editor |
| `src/ui.rs` | Rendering, text layout, and layered windows |
| `src/taskbar.rs` | Taskbar discovery and placement |
| `src/time.rs` | Windows time zones and formatting |
| `src/settings.rs` | Registry persistence and settings migration |
| `src/update.rs` | Background GitHub release checks, verified downloads, replacement and restart |

`--preview-style` opens an isolated appearance editor without changing saved settings. `--verify-overlays` writes `overlay-verification.log` with Windows hit-test and position checks. `--inspect-taskbar` writes taskbar accessibility diagnostics. Logs and build output are ignored by Git.

`--watch-taskbar` observes the running clock for 20 seconds and writes `taskbar-stacking.log`, recording visibility, ownership, and whether the taskbar covers it. This diagnostic does not record window titles or user settings and does not change the running app.

## Releases

GitHub Actions checks formatting, runs Clippy and tests, and builds the executable on Windows. Pull requests produce a downloadable build artifact.

After a successful push to `main`, the workflow publishes a release **only when the version in `Cargo.toml` has no existing GitHub release**. For a new release, update the package version and `CHANGELOG.md` together. Existing releases are left unchanged. A manual workflow run on `main` can retry publication after a failed run.

Release assets are `WorldClock-vVERSION.exe` (for example, `WorldClock-v0.4.1.exe`) and `SHA256SUMS.txt`. The version comes from `Cargo.toml`; the tag is `vVERSION`, and the release title is `World Clock VERSION`. Each release currently offers one executable for x64 Windows, so omit an architecture suffix. Add `-x64`, `-x86`, or `-arm64` only if the same release offers multiple executable architectures. Build products belong in releases, not in the source tree. Contributions are provided under the project's [MIT license](LICENSE).

The updater accepts newer stable `vMAJOR.MINOR.PATCH` tags and requires the executable filename to match that release's version exactly. It uses the same filename to find its SHA-256 entry. Releases before 0.4.1 used `WorldClock.exe` and had no built-in updater; users of those versions need one manual download. Do not rename assets in historical releases or upload unversioned aliases. A release without both uploaded assets is reported as incomplete and can be retried. Keep the checksum file in the format generated by `build.ps1`. The optional network integration test downloads the public latest release and verifies its executable: `cargo test --locked update::tests::live_github_release_and_checksum -- --ignored`.

Prepare release notes in English with concrete verified changes since the preceding published stable release, grouped under Added, Improved, and Fixed when applicable. Include relevant upgrade instructions and platform requirements; a compare link may supplement the notes. The release workflow uses the matching `CHANGELOG.md` entry. Repository uploads and remote GitHub changes use the connected GitHub plugin; the existing release workflow publishes build artifacts with its scoped Actions token.
